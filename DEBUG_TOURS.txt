2. POURQUOI LE DEBIT TOMBE A LA MOITIE
--------------------------------------------------------------------------------

Ton decompose() ne produit qu'UN SEUL chemin :

    start -> gate_hell1 -> maze_trap_a1 -> maze_trap_a2 -> micro_gate1
          -> overflow_hell1
          -> conv_restricted1 -> conv_restricted2 -> conv_restricted3
          -> final_merge -> final_torture1..5 -> impossible_goal

Et il ne produit qu'un chemin parce que maxflow = 1.

IMPORTANT : ce maxflow = 1 est CORRECT. Regarde la map :

    final_torture2  max_drones=1
    final_torture3  max_drones=1
    final_torture4  max_drones=1
    final_torture5  max_drones=1

Elles sont en serie et c'est le seul acces au goal. Ton Ford-Fulkerson ne se
trompe pas. Ne cherche pas de bug dans residual_graph.py.

Le probleme est ce que tu FAIS de ce resultat.

Ton chemin traverse conv_restricted1/2/3 : toutes en zone `restricted` avec
max_drones=1. Or une zone restricted cap=1 ne peut recevoir un nouveau drone
que TOUS LES 2 TOURS. Deroule :

    tour T     | drone A arrive dans conv_restricted1
    tour T+1   | A passe in_flight vers conv_restricted2
               | -> conv_restricted1 est libre a partir de maintenant
    tour T+2   | drone B peut enfin arriver dans conv_restricted1

    => une chaine restricted cap=1 debite 0,5 drone / tour

Alors que le goulot final (final_torture, zones NORMALES cap=1) accepte
1 drone / tour :

    tour T     | drone A arrive dans final_torture2
    tour T+1   | A part vers final_torture3, B arrive dans final_torture2

    => une chaine normale cap=1 debite 1 drone / tour

Ton chemin unique est donc bride a 0,5 alors que la sortie peut absorber 1.
Tu utilises la moitie de la capacite de la map.

5. BUG N°1 : LA REPARTITION PAR BLOCS  (le plus facile, commence par la)
--------------------------------------------------------------------------------

Regarde Simulator.load_drones :

    id = 0
    j = 0
    for i in count_d:
        for _ in range(i):
            self.drones.append(Drone(id, paths[j]))
            id += 1
        j += 1

Avec paths = [A, B, C] et count_d = [9, 8, 8], ca donne :

    drones 0 a 8   -> chemin A
    drones 9 a 16  -> chemin B
    drones 17 a 24 -> chemin C

C'est une repartition PAR BLOCS CONTIGUS.

Maintenant regarde run() :

    self.drones = sorted(self.drones, key=lambda j: j.index, reverse=True)

Au depart tous les drones ont index = 0. Le tri de Python est STABLE : a
valeur egale, il conserve l'ordre d'insertion. Donc l'ordre reste 0, 1, 2, ...

Consequence : les 9 premiers drones s'engouffrent TOUS sur le chemin A avant
que le moindre drone ne touche le chemin B. Tes chemins paralleles sont
utilises SEQUENTIELLEMENT. Tu paies le prix de 3 chemins sans en avoir le
benefice.

Mesure (3 chaines paralleles, memes chemins, meme repartition) :

    repartition par blocs   [9,8,8] -> 68 tours   ecarts = 2,2,2,2,2,2,...
    repartition round-robin         -> 46 tours   ecarts = 1,1,1,1,1,1,...

    22 TOURS D'ECART juste sur l'ordre d'affectation des id.

CE QU'IL FAUT FAIRE :
  Le drone k doit partir sur le chemin k % len(paths), en respectant quand
  meme les quotas de count_d (un chemin qui a recu tous ses drones sort de la
  rotation).

  Piste : au lieu de deux boucles imbriquees "pour chaque chemin, pour chaque
  drone", fais UNE boucle "tant qu'il reste des drones a placer" qui tourne
  sur les chemins et decremente une copie de count_d.

  Attention a garder les id consecutifs a partir de 0 (le format de sortie
  D<ID>-<zone> du sujet ne l'impose pas, mais c'est plus lisible).

  Verifie avec un petit print que tu obtiens bien :
    drone 0 -> chemin 0, drone 1 -> chemin 1, drone 2 -> chemin 2,
    drone 3 -> chemin 0, ...

6. BUG N°2 : calcul_max_turns IGNORE LE DEBIT
--------------------------------------------------------------------------------

    def calcul_max_turns(self, paths):
        count_d = [0] * len(paths)
        turn_paths = [self.path_cost(path) for path in paths]
        for _ in range(self.total_drones):
            i = min(range(len(paths)),
                    key=lambda j: turn_paths[j] + count_d[j])
            count_d[i] += 1
        return count_d

La formule "cout du chemin + nombre de drones deja places" est la formule
classique. Mais le "+ count_d[j]" suppose implicitement qu'un chemin avale
1 DRONE PAR TOUR.

C'est faux pour un chemin qui contient une zone restricted cap=1 : il en
avale 1 tous les 2 tours. Il faudrait :

    turn_paths[j] + count_d[j] * periode[j]

ou periode[j] = 2 si le chemin contient une zone restricted saturante,
1 sinon. (Version simple pour commencer ; le cas exact depend aussi de
max_drones et de max_link_capacity.)

REMARQUE : tu as deja ecrit _get_nb_drone_min() dans graph.py, qui calcule la
capacite minimale le long d'un chemin. ELLE N'EST APPELEE NULLE PART. C'est
exactement la brique dont tu as besoin ici, a moitie ecrite. Relis-la, elle
te donnera le "combien de drones tiennent en parallele sur ce chemin", qu'il
faut croiser avec le cout d'entree des zones restricted.

7. BUG N°3 : decompose() S'ARRETE AU MAX FLOW  (le vrai chantier)
--------------------------------------------------------------------------------

C'est le plus gros et le plus interessant a defendre en soutenance.

maxflow = 1 ne veut PAS dire "1 chemin suffit". Il faut continuer a chercher
des chemins tant que le DEBIT cumule de ton jeu de chemins est inferieur a la
capacite du goulot de sortie.

Note que ces chemins supplementaires n'ont pas besoin d'etre disjoints :
mes 2 chemins de la section 4 partagent tout le debut (start -> micro_gate1)
et toute la fin (final_merge -> goal). Ils ne se separent que sur le segment
restricted, la ou le debit coince. C'est exactement ce qu'il faut.

PISTE (sans tout refaire) :
  1. Fais ta decomposition de max flow comme aujourd'hui.
  2. Estime le debit du jeu de chemins obtenu (somme des 1/periode[j]).
  3. Estime la capacite du goulot de sortie (la fin du chemin, zones normales
     cap=1 -> 1 drone/tour).
  4. Tant que debit < capacite de sortie : cherche un chemin alternatif qui
     evite les zones deja saturees (par exemple un Dijkstra ou tu penalises
     fortement les noeuds deja utilises par les chemins retenus), ajoute-le,
     recalcule le debit.

Ca ne sera pas optimal au sens mathematique, mais ca capture le cas de cette
map et de toutes les maps "hard".

9. COMMENT VERIFIER
--------------------------------------------------------------------------------

Mesure la SUITE DES ARRIVEES, pas seulement le total. C'est ce qui te dit ou
tu bloques :

  - compte a quel tour apparait "impossible_goal" (ou le nom du end_hub) dans
    chaque ligne de sortie
  - calcule les ecarts entre deux arrivees consecutives

  ecarts = 2, 2, 2, 2, ...  -> tu es bride par une chaine restricted
  ecarts = 1, 1, 1, 1, ...  -> tu satures le goulot, tu es a l'optimum
  ecarts irreguliers        -> conflit / attente quelque part, regarde quel
                               noeud revient le plus souvent dans les tours
                               ou personne n'avance

Formule de reference pour savoir si tu es au bout :

    tours_min = path_cost(chemin le plus court) + (nb_drones - 1) / debit_total

  Sur cette map : 19 + 24 / 1 = 43.

    easy   < 10 tours
    medium 10-30 tours
    hard   < 60 tours
    challenger : record de reference 45 (optionnel, ne compte pas dans la note)

Pense a relancer les maps easy/medium/hard apres chaque changement : le
round-robin modifie l'ordre des drones, donc l'ordre des mouvements dans ta
sortie. Le format D<ID>-<zone> reste valide, mais les lignes changent.
